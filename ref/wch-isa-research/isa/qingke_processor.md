# QingKe processor / EVT evidence notes

## Scope and method

This is a maintenance note for a GCC/binutils-based WCH-compatible toolchain, not a claim about any binary-only toolchain.  Conclusions below come only from the four processor manuals, read-only EVT material under `tmp/wch-evt/`, and read-only compiler/binutils probes against the locally supplied WCH toolchains.  Manual citations use the **physical PDF page number**, counting the cover as page 1 (the extracted form prefixes each page with `PDF PAGE n`); source-file citations include their local path and normally a line anchor.  The extraction and per-package configuration evidence are retained in `tmp/wch-evt/eval/`.

Important rule: an EVT project setting is evidence of what that demo requested, not proof that every instruction selected by a corresponding `-march` spelling is executable.  In particular, `XW`, `MRS`, and the WCH interrupt ABI must remain explicit target features whose assembler/compiler behavior is validated, rather than being silently folded into a standard ISA string.

### V2 details

V2 is the ABI outlier: it implements RV32E's 16 GPRs, so any compiler port must use an E ABI/multilib rather than assume `ilp32`; the manual itself does **not** spell a GCC `-mabi` value.  V2C's `m` is explicitly only multiply / `Zmmul`, not full M (`QingKeV2_Processor_Manual.PDF`, PDF pp. 2–3).  XW names `c.lbu`, `c.lhu`, `c.sb`, `c.sh`, and stack-relative forms; the manual says they require MRS or its supplied toolchain (PDF p. 3).  Local GCC12 and GCC15 both accept `rv32ec_zmmul_xw` with `ilp32e` and provide matching multilibs, but their object attributes encode different E/XW versions; interoperability must therefore be tested at the attribute/link boundary rather than inferred from the token spelling.

PFIC has fixed internal vectors 0–15 and external vectors 16–255, supports fast hardware save/restore and two VTF direct-vector channels (`QingKeV2_Processor_Manual.PDF`, PDF pp. 8, 16–17).  Fast functions use `__attribute__((interrupt("WCH-Interrupt-fast")))`; conventional software-stack functions use `__attribute__((interrupt()))` (PDF p. 17).  HPE saves ten caller-saved integer registers in the user stack and only supports two levels (PDF pp. 16–17).  The manual says V2 has only M mode and no PMP (PDF pp. 3, 5).  The V2A startup confirms an M-mode boot (`mstatus=0x1880`) at `tmp/wch-evt/evt/QingkeV2A_CH32V003_EVT/EXAM/SRC/Startup/startup_ch32v00x.S:165`.

### V3 details

V3 moves to the 32-GPR RV32I register set.  The manual's variant table is more precise than a family-wide `rv32imac`: B and C differ in optional M/B, V3F adds scalar F, and V3V exposes `Zve64x_zvbb` plus vector CSRs/64-bit VLEN (`QingKeV3_Processor_Manual.PDF`, PDF pp. 2–3, 51–53).  Do not describe B as atomic merely because a modern project UI can tick an atomic checkbox: chapter 9 reports AMO only for V3A and V3F, not B/C (PDF p. 54), while the overview explicitly says V3A's LR/SC is simplified to load/store and SC always succeeds (PDF p. 2).  The same table confirms the MRS shift-multiply extension only for V3B; its `mimpid[7:0]=3` note adds a custom delay instruction and `Zicond` (PDF pp. 54–56).  The manual does not label a separate DSP ISA; B, MRS, and V3V vector/bitmanip facilities are the direct evidence.

V3 has four VTF channels and two HPE levels; V3B's PFIC vector behavior differs enough that its table permits address/instruction modes while V3A is instruction-only (`QingKeV3_Processor_Manual.PDF`, PDF pp. 3, 8–9).  PMP is absent in V3B but present for V3A/C/F/V, up to four regions (PDF pp. 3, 26–30, 54).  Vector caller preservation may be standard or variant ABI under `vcontrol`; it needs a compiled-call test before enabling vector multilibs (PDF p. 6).

### V4 details

V4 standardizes the stated `IMAC` base, adds F only on V4F, and retains XW except V4A.  Its documented A extension maps LR/SC to load/store and makes SC always succeed (`QingKeV4_Processor_Manual.PDF`, PDF p. 2), so it cannot be treated as a general multiprocessor atomic implementation without a silicon-level qualification.  The V4F fast-HPE path still requires compiler software preservation of floating registers (PDF p. 18); this is a material hard/soft-float calling-convention probe.  V4 provides four VTF channels and 256 PFIC entries; the manual again assigns `WCH-Interrupt-fast` to HPE handlers and plain `interrupt()` to software-stack handlers (PDF pp. 9, 18–19).  All documented variants have a PMP interface, but the comparison table reports zero implemented regions for V4B (PDF pp. 3, 19–23).

V4J alone is documented with I-cache.  The CSR list (`cstrcr`, `cpmpocr`, `cmcr`, `cinfor`) makes cache operations and cache/PMP interaction assembler/builtin candidates, but neither a GNU builtin name nor an instruction mnemonic is supplied (`QingKeV4_Processor_Manual.PDF`, PDF pp. 31–37).  The cache is therefore a target-specific CSR interface, not a standard cache extension assertion.  External debug is 0.13.2; WCH protocol revision and single-/two-wire availability differ by variant (PDF pp. 29–30).

### V5 details

V5F is the broadest scalar profile: `I M A B C F` plus XW, dynamic branch prediction, 7–9 pipeline stages, FPRs, and eight HPE/nesting levels (`QingKeV5_Processor_Manual.PDF`, PDF pp. 2–6).  Its HPE writes 16 caller-saved integer registers to DTCM at CSR `0xBC4` rather than the V2 user stack (PDF pp. 18–19, 42); this makes the WCH fast-interrupt prologue/return and DTCM reservation a distinct V5 ABI/runtime issue.  TCM/cache policy, access and information CSRs include `0xBC2`–`0xBC6`, `0xBD0`, and `0xFC0`; exact capacities are implementation-reported, not family constants (PDF pp. 35–47).  Debug 0.13.2 includes hardware instruction/data breakpoint support (PDF pp. 25–26).

## Compiler/binutils implications, observed behavior and probe queue

### ISA spelling, versions, predefined macros and multilibs

The local references are GCC 12.2.0 (`MRS_Toolchain_MAC_V240/Toolchain/RISC-V Embedded GCC12/bin/riscv-wch-elf-gcc`) and GCC 15.2.0 (`MRS_Toolchain_MAC_V240/Toolchain/RISC-V Embedded GCC15/bin/riscv32-wch-elf-gcc`). The bundled GCC8 executable is x86-only and cannot run on this arm64 host. `-print-multi-lib` confirms both E/`ilp32e` and I/`ilp32`, XW, Zmmul, bitmanip, and single-hard-float `ilp32f` families. GCC15 additionally has a V3V-shaped vector multilib and spells A's components as `zaamo_zalrsc`; exact normalized entries are in `tmp/wch-evt/eval/toolchain-probes.md`.

The same tokens do not mean identical attributes across compiler releases. For a V2-shaped object, GCC12 writes `rv32e1p9_c2p0_xw1p0`; GCC15 writes `rv32e2p0_c2p0_zca1p0_xw2p0`. Full-register objects similarly gain explicit B/`zaamo`/`zalrsc`/`zca`/`zcf` components in GCC15. GCC12 defines `__riscv_xw` as `0`, whereas GCC15 reports version `2000000`; E changes from `1009000` to `2000000`. A port should compare canonicalized feature sets and attributes, not string equality or truth-test `__riscv_xw`. The processor manuals name architecture features but do not assign these GNU extension versions, so the intended silicon-to-version mapping is **待确认**.

### ABI, stack, return and interrupt attributes

Compiled objects confirm a 4-byte stack-alignment attribute for RV32E/`ilp32e` and 16-byte alignment for RV32I/`ilp32` and `ilp32f`. Both tested compilers accept `__attribute__((interrupt()))` and `__attribute__((interrupt("WCH-Interrupt-fast")))`; normal and fast handlers return with `mret`. On small integer probes, a normal handler builds a software save frame while the fast form relies on HPE and saves no GPR. This matches the manual distinction (`QingKeV2_Processor_Manual.PDF`, PDF p. 17; V3 PDF p. 18; V4 PDF p. 18; V5 PDF p. 19), but it does not by itself validate nesting/CSR setup.

For a hard-single handler, both releases save used FPRs in software even in the fast form, consistent with the V4F manual. GCC15's normal handler also saves/restores FCSR; GCC12's does not, and neither tested fast handler did. GCC15 also saves an extra `t0` in the normal integer handler. These are confirmed code-generation differences but their correctness/erratum status is **待确认**; they require runtime interrupt/nesting and FP-exception probes before treating one release as authoritative. EVT startup always returns to `main` with `mret`; representative reset sequences are `tmp/wch-evt/evt/QingkeV2A_CH32V003_EVT/EXAM/SRC/Startup/startup_ch32v00x.S:165`, `tmp/wch-evt/evt/QingkeV3B_ CH32V205_EVT/EXAM/SRC/Startup/startup_ch32v205.S:296`, `tmp/wch-evt/evt/QingkeV3F_CH32X315_EVT/EXAM/SRC/Startup/startup_ch32x3x5.S:241`, `tmp/wch-evt/evt/QingkeV3V_CH32V407_EVT/EXAM/SRC/Startup/startup_ch32v4x7.S:356`, and `tmp/wch-evt/evt/QingkeV5F_CH32H417_EVT/EXAM/SRC/Startup/startup_ch32h417_v5f.S:480`.

### CSR/builtin, assembler, linker and workaround implications

EVT core headers use inline `csrr/csrw`, `fence.i`, and PFIC MMIO at `0xE000E000`; no manual-proven GCC builtin names were found. Keep PFIC, HPE, PMP, cache/TCM and V3V CSRs as explicit target/runtime interfaces until builtin spelling and clobber semantics are specified. Device IRQ numbering is not uniform: V2A external IRQs start at 16 (`tmp/wch-evt/evt/QingkeV2A_CH32V003_EVT/EXAM/SRC/Peripheral/inc/ch32v00x.h:44`), while CH32H417 has two SysTicks, IPC internal entries 16–19, and external WWDG at 32 (`tmp/wch-evt/evt/QingkeV5F_CH32H417_EVT/EXAM/SRC/Peripheral/inc/ch32h417.h:47`, `:50`, `:57`). A generic CRT must therefore consume the device table rather than assume one family-wide vector enumeration.

Both local assemblers accept the XW `c.lbu`, `c.lhu`, `c.sb`, and `c.sh` mnemonics under an `_xw` profile and emit 16-bit instructions, but their paired `objdump` prints raw `.2byte`/`.insn` instead of decoding them. Both also assemble and disassemble `mcpy`, `mrslu`, `mrsl`, and `wexti`; only the V3 manual's B/C memory-copy note and V3B MRS table directly support part of that set (`QingKeV3_Processor_Manual.PDF`, PDF pp. 3, 54). `wexti` and broad cross-generation availability remain **待确认**. This is a concrete GAS/objdump port gap, not evidence that every accepted mnemonic works on every core.

`ld` support must preserve `ENTRY(_start)`, `.init`/`.vector`, `KEEP`, the global-pointer convention, high-code/data copy symbols, and package-specific memory regions. V3C requires 1 KiB-aligned RAM vectors; V3V reserves low RAM; V5F splits load, ITCM code/vector and DTCM data, with HPE/runtime reservation. IAP, application-offset, and RunInRAM scripts are intentional alternate layouts. No labelled processor errata were found in the four manuals; `corecfgr`, the V3 `mimpid=3` delay feature, FCSR-save differences, and stale/copied project profiles are workaround/probe leads, not proven errata.

## Manual/demo agreement and open evidence

Confirmed manual-only or underused features include V3F and V4F hardware F despite no hard-float setting in their readable EVT configs, V4J's I-cache despite no V4J EVT package, and V5F F despite only three hard-float V5F configurations. Confirmed demo-only or over-broad requests include V3F project rows carrying a V3V vector string, V3V rows carrying CH32V205 settings, and the shared V5 core header's `ASM_MCPY` even though the V5 manual does not confirm memory-copy ISA support. These rows must not enlarge a core's supported ISA.

The remaining **待确认** items are: (1) a genuine CH32V006/V2C package and flags; (2) independent evidence distinguishing the supplied V4B and V4C trees; (3) exact flags for the 656 opaque `.wvproj` descriptors, especially V2A/V3A; (4) silicon/runtime validation of interrupt save sets, FCSR, fast-FP nesting, V3V vector calling convention, and V3A/V4 simplified LR/SC; (5) the intended XW version and any `wexti`/memory-copy availability outside the manual-confirmed V3 variants; and (6) processor-level external bus details, which these processor manuals do not specify.
